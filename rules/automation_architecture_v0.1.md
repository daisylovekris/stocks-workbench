# 股票小工坊自动化总蓝图｜v0.1

## 一、总目标

股票小工坊要做的，不是“自动炒股机器人”，而是一个有闸门的工作台：

- 事实自动化
- 规则拦截
- 叙事生成
- 预测参考

核心原则：

- 不自动交易
- 不把预测当保证
- 不把观察条件写成执行动作
- 不让 LLM 编造行情真值
- 不让人工继续做重复性核对

一句话概括：

> 脚本负责事实，规则负责拦截，LLM 负责叙事，预测只做参考。

## 二、目录与风险

### 1. 目录规划

建议先把目录落点定死，避免脚本乱放：

- `data/daily/` 放 `facts pack`
- `config/` 放关键位配置、lint 规则
- `tools/` 放脚本
- `reports/validation/` 放校验报告
- `logs/` 放运行日志

### 2. 全局风险等级

建议统一定义全局风险等级：

- `P0`：会导致错误交易倾向、自动动作、事实伪造
- `P1`：会导致复盘结论错位、关键位身份错误
- `P2`：旧口径残留、当前区未同步、轻度表述越界
- `P3`：格式、索引、引用、标题类问题

## 三、自动化架构

建议拆成 5 层：

### 1. 采集层

负责抓取：

- 行情
- 公告
- 新闻
- 板块
- 资金面
- 历史样本

### 2. 归一层

负责把输入统一成可用结构：

- 统一字段
- 统一日期
- 统一交易日口径
- 统一关键位状态
- 统一消息分类标签

### 3. 校验层

负责拦截错误：

- 旧口径残留
- 动作化表达
- “硬底 / 支撑 / 风险解除”误写
- git 漏项
- 事实与文本不一致

### 4. 生成层

负责产出文档草稿：

- 每日复盘
- 周观察
- 持仓卡更新
- 风险卡更新
- 估值卡更新
- 股性分析专题

### 5. 输出层

负责最终落盘：

- 自动写 Markdown
- 必要时更新索引
- 必要时生成审计日志
- 可选推送到常用查看位置

## 四、任务编排 / 合约层

这里吸收 `repo-harness` 的工作流骨架，但只保留适合股票小工坊的部分。

建议把任务编排理解为“可执行合约”：

- `contract.template.md` 的思路 → Phase 1 任务卡模板
- `review.template.md` 的思路 → 封箱复核卡模板
- `handoff-protocol.md` 的思路 → 夜班交班模板
- `check-task-workflow.sh` 的思路 → `seal_check.py` 设计参考
- `check-task-sync.sh` 的思路 → 文件改动与任务卡同步检查参考
- worktree 隔离 / bounded task / bounded commit → 未来执行隔离策略参考

这个层主要负责：

- 任务边界
- 停止条件
- 允许路径
- 证据链
- 交接和续接

它不负责行情、不负责叙事，只负责把后面的脚本和文档纳入可控工作流。

## 五、最优先的脚本

我们把优先级收紧成四个先做：

### 1. `validate_review_chain.py`

优先级最高。

作用：

- 扫当前判断区 / 当前状态区 / 当前结论区 / 新增或本轮编辑范围中的旧日期残留
- 扫动作化表达
- 扫“硬底 / 支撑 / 风险解除 / 加仓成熟”等误写
- 扫价位身份滑坡
- 扫文本口径和事实不一致
- 区分历史日期小节与当前判断区：历史小节中的历史事实可以保留，当前判断区中的旧口径必须拦截
- 未来还必须支持“当前区旧口径残留检测”：先识别历史日期小节、当前背景、当前主矛盾、当前纪律、当前结论、分层观察区、本卡当前结论以及 staged diff 变化范围，再判断命中是否需要拦截
- 未来还必须支持按 section 语义识别当前区，不能只用文件位置或最近日期小节判断历史 / 当前
- 下列 heading pattern 应默认识别为当前区：`当前*`、`本卡当前结论`、`当前纪律`、`分层观察区间`、`当前不能*`、`可以进入*`、`重新评估*`、`需要补充的数据`
- 对这些当前区中的旧日期、旧价位、旧量比、旧结论命中，应标为 P2
- 对旧日期、旧价位、旧量比、旧结论的检测必须结合 section 语义；历史区命中只报告为历史保留，当前区命中应标为 P2
- 对 staged diff 中新增日期小节但未同步当前通用区的情况，应标为 P2
- 对“未见公告 / 无新增公告级重大利好利空”类表达，要结合 facts pack 的 `needs_manual_check` 状态判断是否越权，而不是全文件无差别误杀

特点：

- 不依赖外部数据源
- 今天就能写，今天就能跑
- 最适合先拿现有所有复盘文件做体检
- 默认不做全文件无差别误杀；必须按章节语义、当前判断区、当前结论区、本轮新增区或 staged diff 变化范围来判断命中是否有效

### 2. `seal_check.py`

作用：

- 检查本次预期封箱文件清单
- 检查 staged commit set 是否只包含预期文件
- 检查与本次封箱相关的 `untracked / AD / AM / MM`
- 检查 staged diff
- 检查 index 引用的新文件是否已经纳入暂存
- 检查是否存在敏感文件、缓存文件或明显误入暂存的文件

建议：

- 可以做成 `pre-commit hook`，但默认只约束 staged commit set 和本次预期文件清单
- 不应要求整个工作区绝对干净；如果存在与本次提交无关的未暂存改动或 untracked 文件，应提示并要求确认归属，而不是无条件阻断所有 bounded commit
- 对本次提交相关文件中的 `?? / AD / AM / MM` 半状态必须阻断
- 对 staged 区中的非预期文件、敏感文件、缓存文件必须阻断
- 让“忘记跑 staged 检查 / 漏加新文件 / 半状态封箱”在机制上不可能发生

### 3. `derive_level_status.py`

作用：

- 把关键位身份从人工描述变成脚本结论
- 这是整个复盘链最容易出错的地方

输出示例：

- 盘中触及
- 盘中突破
- 收盘站上
- 收盘跌破
- 连续维持
- 未进入
- 未收回

### 4. `fetch_daily_quote.py`

作用：

- 抓行情事实
- 产出每日事实包
- 后续可接腾讯 / AKShare / 其他源

说明：

- 这部分最容易碰字段坑、接口差异、代理问题
- 所以放在前面的校验和身份逻辑之后更稳
- 现有 `tools/akshare_daily_quote_check_v0.1.py` 是 `fetch_daily_quote.py` 的前身 / 试验版；后续优先基于现有脚本演进，不急于新开平行脚本，避免职责重叠。

## 六、facts pack 和 levels.json 要分离

这是我们特别认同的一点。

### 1. `facts pack`

建议作为每日事实快照保存，例如：

- `data/daily/300274_YYYY-MM-DD_facts.json`

建议包含：

- `schema_version`
- `generated_at`
- 当日行情字段
- 公告状态
- 新闻状态
- 板块和大盘背景
- 量比候选来源
- 缺失字段显式标记为 `unknown` / `needs_manual_check`

原则：

- 不要强行填满空字段
- 不要假装今天没有缺失

建议为需要人工或多源确认的字段统一加入 `verification` 结构，例如：

```json
{
  "verification": {
    "status": "candidate | confirmed | conflict | needs_manual_check",
    "confirmed_by": "manual_ths | script | multi_source | none",
    "notes": ""
  }
}
```

适用字段包括但不限于：

- 量比
- 板块红绿
- 公司公告级重大利好 / 利空
- 外部政策预期消息
- 新闻分类标签

原则：候选数据和确认数据必须分开保存；候选量比、候选消息、候选公告结论不得直接进入正式主链。

### 2. `levels.json`

不要把它做成静态说明文档，而要做成每日动态身份结果。

建议结构分成两层：

- `config/300274_levels.yaml`
  - 人工维护的关键位配置
  - 禁写规则
- `data/daily/..._levels.json`
  - 脚本按当日 OHLC 和历史序列动态生成

### 3. 身份逻辑

身份必须是函数，不是文案。

身份 = `f(配置, 当日OHLC, 历史序列)`

例如：

- `127.18`：跌破 / 未收回 / 连续几日收于其下
- `138.61`：心理锚，不是硬底
- `145 / 150 / 153—155 / 157 / 160`：按日推导身份

### 4. 可回查性

建议增加：

- `source_snapshot_id`
- 或 `facts_hash`

作用：

- 防止 facts pack 对了，但复盘文本抄错了
- 让复盘和事实包能互相核验

## 七、每日报告自动流程

推荐顺序：

1. 抓行情、公告、新闻、板块、资金面
2. 生成 `facts pack`
3. 生成 `levels.json`
4. 生成 `validation report`
5. 生成日复盘草稿
6. 封箱、落盘、必要时更新索引

也就是：

- 先事实
- 再身份
- 再校验
- 最后叙事

这比“先写完整复盘再回头核对”稳得多。

## 八、消息面自动化怎么替代 Perplexity

不是找一个“Perplexity 替代品”，而是把它拆开。

### 1. 公告级消息

尽量代码化。

建议路径：

- 官方源 / 巨潮资讯 / AKShare 拉公告列表
- 官方公告源查询成功且无结果，才写“无新增公告”
- 如果公告源查询失败、网络失败、解析失败或结果不确定，必须写“公告检查失败 / 待人工核对”，不得把失败误写成“无新增公告”
- 官方公告、交易所披露、监管文件、公司正式披露可单源确认
- 非官方消息至少 2 个独立来源才算强证据
- 有公告再让 LLM 做标题和摘要分类

目标：

- 把“无新增公告级重大利好 / 利空”尽量变成代码事实

### 2. 行业 / 板块新闻

建议路径：

- RSS / RSSHub / 公开财经源聚合
- 关键词过滤
- LLM 分类

### 3. 交叉验证

交叉验证应变成规则，而不是人工记忆。

例如：

- 对非官方新闻、媒体消息、社交平台消息，同一事件至少 2 个独立来源才算强证据
- 官方公告、交易所披露、监管文件、公司正式披露属于一手权威源，可单源确认
- 若官方源与媒体源冲突，以官方源优先，并标记媒体源为待复核
- 单源非官方消息标注“待确认”
- 多源冲突标注“待人工”

## 九、预测工具的使用规则

预测工具可以保留，但只能在参考层。

补充边界：Phase 5 之前，预测工具不进入日常主链；只允许在股性研究、周六专题或情景参考附录中试用。预测输出不得改写事实复盘主结论，不得触发任何交易动作。

### 1. 正确用途

- 输出概率参考
- 输出情景排序
- 输出风险提示
- 输出结构状态

### 2. 错误用途

- 直接写成买卖建议
- 直接当最终结论
- 用单次预测替代复盘
- 把历史胜率当未来保证
- 用黑箱输出接管纪律

### 3. 推荐优先级

#### 第一优先

1. `vectorbt`
   - 最适合做股性统计
   - 最适合做关键形态后的历史表现
   - 最适合周六专题

2. `Qlib`
   - 最适合做研究框架、因子、标签、实验管理
   - 更适合长期研究平台

#### 第二优先

3. `FinNLP`
   - 适合财经文本、新闻、公告的分类与摘要

4. `FinGPT`
   - 适合财经文本理解和摘要

#### 第三优先

5. `FinRL`
   - 可以看
   - 但更偏策略实验
   - 不建议早期上主链

### 4. 输出形式

预测结果最好长成这样：

- 情景 A：延续
- 情景 B：反抽
- 情景 C：震荡
- 情景 D：破位
- 每个情景给概率区间
- 再给一个当前最需要警惕的情景

并且附上限制：

- 样本不足
- 不构成交易建议
- 不替代事实复盘
- 不进入主链结论

## 十一、小工权限边界与牵引绳规则

自动化不是放任小工自由发挥，而是把每一步都放进可审计的闸门。

### 1. 只读任务

- 只读审计不得修改文件。
- 只读审计不得 `git add` / `git commit` / `git push`。
- 只读审计只能列出问题、位置、风险等级和建议修法。

### 2. 路径建议任务

- 如果任务要求“查找命名规则 / 建议路径 / 等待用户确认”，小工必须在给出路径建议后停止。
- 不得擅自创建文件。
- 不得擅自修改 index。
- 只有用户明确确认后，才允许进入创建 / 修改阶段。

### 3. 修改任务

- 修改任务必须限定允许修改的文件。
- 不得扩展任务范围。
- 不得自动解释 codebase。
- 不得读取 `.env`、token、secret 或其他敏感信息。
- 不得把观察条件写成动作条件。

### 4. 暂存与封箱任务

- 修改完成后必须先做 staged 检查，再 review，再 commit。
- staged 检查不得自动 commit。
- review 通过前不得封箱。
- commit 后不得自动 push。
- staged 检查必须以“本次预期文件清单”为准，不得把无关工作区脏状态一概视为本次封箱失败。
- 如果存在无关未暂存改动或 untracked 文件，必须单独列出并确认归属；只有与本次提交相关、敏感、缓存、半状态或会导致引用断链的文件才阻断封箱。

### 5. rename 与编辑器旧 tab

- 文件 rename 后，必须同时处理旧路径删除与新路径新增。
- `git status` 中不得留下 `AD` / `AM` / `??` 半状态。
- rename 后必须重新打开新路径文件核对。
- VS Code / 编辑器中旧路径 tab 可能是 stale view；不得根据旧路径 tab 判断最终内容。
- 审计时以 `git status`、真实新路径文件和 `git diff` 为准。

### 6. 周观察特殊规则

- 周日观察文件名必须使用真实周日日期。
- 标题日期必须与文件名一致。
- 观察范围必须是下一交易周的实际交易日区间。
- 一般情况下为周一至周五。
- 若遇到法定节假日、调休、临时休市或交易日调整，必须按交易所实际交易日口径修正。
- 周日观察不能只写上周五收盘状态，必须补充上一交易周路径回顾。
- 历史数据必须来自已封箱日复盘或 index，不得编造。
- 周观察只建立观察框架，不输出买卖动作。

## 十二、最终共识版一句话

> 股票小工坊自动化要先做事实包、价位身份、校验器和封箱钩子，先把最累最易错的部分替掉；LLM 只负责叙事与归纳，预测工具只放参考层，不进主链，不做交易动作。
